# Session to Skill

현재 대화의 성공 패턴을 그대로 복사하지 않고, 다른 세션에서도 실행 가능한 Claude Code 스킬 계약으로 재구성한다.

## 언제 사용하면 좋은가

- 여러 번 수정한 끝에 재현 가능한 해결 절차가 확인됐을 때
- 같은 종류의 요청을 앞으로 반복할 가능성이 높을 때
- 사용 도구, 입력, 산출물, 실패 조건, 검증기가 명확할 때
- 프로젝트 팀원이 같은 절차를 Claude Code에서 재사용해야 할 때
- 긴 대화에서 핵심 운영 절차만 분리해 유지보수하고 싶을 때

대표 호출 예시:

- `이 세션을 스킬로 만들어줘`
- `이 대화 내용을 skill로 구성해줘`
- `방금 성공한 워크플로우를 재사용 가능한 스킬로 등록해줘`
- `이 작업 순서를 Claude Code 스킬로 정리해줘`
- `세션에서 스킬 후보를 뽑고 SKILL.md로 만들어줘`

## 사용하지 않는 경우

- 단순한 일회성 답변이나 일반 지식 요약
- 아직 실행·검증되지 않은 아이디어
- 세션에 입력, 산출물 또는 성공 기준이 없는 경우
- 토큰, 쿠키, OAuth 상태, 개인 메시지 등 비밀정보를 절차에 포함해야 하는 경우
- 기존 스킬과 사실상 동일한 경우: 새 스킬 대신 기존 스킬 보강을 우선한다

## 입력

필수 입력:

1. 현재 대화 세션 또는 사용자가 지정한 대화 로그
2. 스킬로 만들고 싶은 작업 범위

선택 입력:

- 원하는 스킬 이름
- 설치 범위: 프로젝트 로컬 또는 사용자 전역
- 관련 파일·로그·테스트·검증 결과
- 포함하면 안 되는 프로젝트명, 경로, 고객정보

## 산출물

기본 산출물:

```text
<target>/
  SKILL.md
  README.md              # 사용법·예시·제한사항, 필요한 경우
  references/            # 반복 참조 자료가 있을 때만
  scripts/               # 검증된 재사용 스크립트가 있을 때만
```

설치 위치:

- 프로젝트 전용: `<project>/.claude/skills/<skill-name>/`
- 사용자 전역: `~/.claude/skills/<skill-name>/` — 사용자가 명시적으로 요청한 경우에만
- 검토용 초안: 사용자가 지정한 staging/output 경로

`.skill` 압축 파일은 전달용 선택 산출물이다. Claude Code의 실제 실행 원본은 디렉터리 안의 `SKILL.md`다.

## 워크플로우

### Step 1. 세션 범위 잠금

- 현재 세션 전체인지, 특정 구간·파일인지 확인한다.
- 사용자가 지정한 범위가 있으면 그 범위 밖 내용을 섞지 않는다.
- 대화에 등장한 비밀정보·개인정보·고객정보는 추출 대상에서 제외한다.

### Step 2. 증거 기반 패턴 추출

다음 항목을 대화와 실제 실행 결과에서 찾는다.

1. 사용자 트리거와 작업 목적
2. 입력과 전제조건
3. 사용한 도구와 실행 순서
4. 실제로 생성·변경된 산출물
5. 실패 신호와 수리 방법
6. 최종 검증 방법
7. 다른 환경에서 바꿔야 하는 경로·도구

추측으로 빈칸을 채우지 않는다. 확인되지 않은 항목은 `미확인`으로 표시한다.

### Step 3. 스킬 승격 적합성 판정

아래 조건을 확인한다.

- 반복 가치가 있는가
- 단계가 다른 세션에서도 실행 가능한가
- 입력·출력·완료 기준이 명확한가
- 성공 또는 실패 후 수리 과정이 실제로 검증됐는가
- 기존 스킬에 흡수하는 편이 더 낫지 않은가

검증되지 않은 아이디어라면 바로 등록하지 말고 `skill candidate`로 제안한다.

### Step 4. 사용자 확인

파일을 등록하기 전에 아래 형식으로 제안한다.

```markdown
## 세션 분석 결과

- 제안 이름:
- 한 줄 목적:
- 권장 사용 시점:
- 사용하지 않을 시점:
- 트리거 표현 5개 이상:
- 입력:
- 핵심 워크플로우:
- 산출물:
- 검증 방법:
- 개인정보·환경 의존성 제거 항목:
- 기존 스킬과의 중복 여부:
```

사용자가 이미 이름·범위·등록 의사를 명확히 승인한 경우에는 같은 질문을 반복하지 말고 그 승인 범위 안에서 작성한다.

### Step 5. SKILL.md 작성

- frontmatter의 `name`은 디렉터리명과 같은 kebab-case로 쓴다.
- `description`에는 기능과 구체적인 호출 상황을 함께 쓴다.
- 본문에는 최소 `언제 사용`, `사용하지 않는 경우`, `입력`, `산출물`, `워크플로우`, `검증`, `실패·복구`를 포함한다.
- 특정 PC의 절대경로 대신 `<project>`, `~`, 환경변수 같은 이식 가능한 표현을 사용한다.
- 외부 전송·삭제·게시·자격정보 변경은 자동 단계로 넣지 않는다.
- 검증되지 않은 스크립트나 명령은 포함하지 않는다.

### Step 6. 구조·행동 검증

최소 검증:

1. YAML frontmatter가 파싱되는가
2. `name`과 디렉터리명이 일치하는가
3. 트리거 표현이 5개 이상인가
4. 입력·산출물·실패·복구·검증 절이 있는가
5. 개인 절대경로, 토큰, 쿠키, OAuth 상태, 고객 식별자가 없는가
6. 저위험 테스트 대화에서 스킬이 의도한 분석 형식을 생성하는가
7. 원본 대화·원본 스킬 파일의 해시가 바뀌지 않았는가

### Step 7. 등록 또는 전달

- 승인된 대상 경로에 스킬 디렉터리를 저장한다.
- 전달용 압축이 필요하면 디렉터리 구조를 유지한 채 `.skill` 또는 `.zip`으로 패키징한다.
- 최종 보고에는 정확한 경로, 포함 파일, 검증 결과, 남은 제한을 적는다.

## 실패와 복구

| 실패 신호 | 처리 |
|---|---|
| 세션 내용이 너무 짧음 | 필요한 작업 범위·입력·산출물을 한 번만 구체적으로 요청한다 |
| 이름이 기존 스킬과 충돌 | 기존 스킬 보강안을 우선 제시하고 새 이름이 필요할 때만 제안한다 |
| 최종 산출물이 불명확 | 등록을 보류하고 `skill candidate`로 남긴다 |
| 검증 결과가 없음 | 검증 절차를 설계한 뒤 저위험 fixture로 먼저 실행한다 |
| 개인 경로·고객명이 발견됨 | placeholder로 일반화하고 재검사한다 |
| 실제 Claude Code에서 로드되지 않음 | frontmatter, 디렉터리명, 설치 범위, skill discovery 상태를 순서대로 점검한다 |

## Anti-rationalization

- 대화 원문을 그대로 붙여 넣는 것은 스킬 작성이 아니다.
- 트리거만 많고 완료 기준이 없으면 재사용 가능한 스킬이 아니다.
- 정적 문법 검사만 통과했다고 실제 사용 검증이 끝난 것은 아니다.
- 사용자 전역 스킬 폴더에 쓰는 것은 명시 승인 없이 수행하지 않는다.
- 스킬 단독 검증 전에는 여러 스킬을 플러그인으로 묶지 않는다.
