# AS-IS to TO-BE Analysis

## 입력 게이트

다음 중 하나 이상의 실제 근거가 없으면 개선안을 확정하지 않는다.

- AS-IS 진단
- 사용자 조사·VOC
- RFP·요구사항
- 벤치마킹 보고서

## 절차

1. 문제를 시스템 표현에서 사용자 영향으로 재서술한다.
2. 문제마다 근거 ID, 영향 사용자, 빈도·심각도, 요구사항을 연결한다.
3. 단순화, 예측 가능성, 오류 방지, 일관성, 피드백, 접근성, 회복 가능성 관점으로 개선안을 도출한다.
4. 공공 서비스면 `references/krds-checklist.md`로 KRDS/KWCAG 점검을 수행한다.
5. 핵심 과업별 AS-IS/TO-BE 흐름과 예외 흐름을 작성한다.
6. 개선안을 화면 단위 요건으로 변환한다.

## 화면 요건 형식

```markdown
## [화면 ID] [화면명]
- 목적 / 대상 사용자 / 진입 경로
- 연결 문제·요구사항·개선 ID
- 화면 유형
- 필수 UI 요소
- 사용자 행동과 시스템 반응
- 상태·예외·오류
- 반응형·접근성·디자인시스템 요건
- 수용 기준
```

## 산출물

사용자가 지정한 출력 루트 아래에 다음을 만든다.

- `tobe-analysis-report.md`
- `screen-requirements.md`
- 공공 서비스일 때 `krds-compliance-report.md`

출력 위치가 지정되지 않으면 현재 프로젝트의 `output/ux-analysis/`를 사용한다.

## 다음 단계

`screen-requirements.md`를 `wireframe-composer`의 주 입력으로 전달한다.

## 완료 조건

- 근거 없는 개선안 없음
- 문제→개선→시나리오→화면 요건 추적 가능
- 공공 서비스 여부와 KRDS 적용 결과 명시
- 미확인 내용은 가정이 아니라 미결사항으로 분리
